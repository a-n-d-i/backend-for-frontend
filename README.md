# APISIX tokenhandler

Python plugin for [Apache APISIX](https://apisix.apache.org/), run through the
[python plugin runner](https://github.com/apache/apisix-python-plugin-runner)
via `ext-plugin-pre-req`.

The plugin is a **Backend for Frontend** (BFF) for browser apps, following
[draft-ietf-oauth-browser-based-apps, section 6.1](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-browser-based-apps#name-backend-for-frontend-bff).
It runs the OpenID Connect login as a confidential client, keeps all tokens in
a server-side session, and gives the browser only an `HttpOnly` session cookie.
On API requests it swaps that cookie for the access token. A Vue SPA in `spa/`
logs in through it.

[docs/oauth-best-practices.md](docs/oauth-best-practices.md) lists the IETF and
OWASP OAuth/OIDC best practices and where each is implemented, or why not.

## BFF endpoints

| endpoint                       | does                                                          |
|--------------------------------|---------------------------------------------------------------|
| `GET /bff/login?return_to=/x`  | start the login, redirect to Dex                              |
| `GET /bff/callback`            | code exchange, ID token validation, session cookie, back to `return_to` |
| `GET /bff/session`             | `{"authenticated": true, "user": {...}}` or `{"authenticated": false}` |
| `POST /bff/logout`             | end the session; `{"logout_url": ...}` if the IdP has RP-initiated logout |
| `* /api/...`                   | forwarded to the API (httpbin) with `Authorization: Bearer`, prefix stripped |

Every request except login and callback needs the header `X-BFF-CSRF: 1`
(CSRF defense); cross-origin requests are refused. The options are in
`DEFAULTS` in `plugins/tokenhandler.py`; the route config in
`conf/apisix.yaml` sets issuer, client and redirect URI.

## Dev container

Open the folder in VS Code and run **Dev Containers: Reopen in Container**.

The container *is* the gateway: APISIX 3.19 (standalone, no etcd) runs in it,
spawns the python runner, and proxies to an `httpbin` echo container.
APISIX listens on <http://localhost:9080>, which is also published to the host.

[Dex](https://dexidp.io/) runs as OIDC provider behind APISIX under `/dex`
(issuer `http://localhost:9080/dex`), so the same URLs work from the browser
on the host and from the tests in the container. It shows its own login form;
user `admin@example.com` / `password`, client `tokenhandler` /
`tokenhandler-secret` with redirect URI `http://localhost:9080/bff/callback`.

The SPA is served by a static server block in the gateway's nginx
(`conf/config.yaml`) behind the catch-all route, so SPA, BFF and Dex share
one origin. Open <http://localhost:9080/> and log in. Use `localhost`, not
`127.0.0.1`: the session cookie is `Secure`, which browsers accept on plain
http only for `localhost` (Chromium and Firefox, not Safari).

Claude Code is installed (`claude` CLI plus the VS Code extension). Its config
and login are kept in the `claude-config` volume, so they survive rebuilds.

The container user's uid/gid default to 1000. If yours differ, export
`USER_UID` / `USER_GID` before building.

```
.devcontainer/      image, compose stack, VS Code settings
conf/config.yaml    APISIX static config incl. the SPA server (`make reload`)
conf/apisix.yaml    routes and BFF config, hot reloaded on save
conf/dex.yaml       Dex config: client and users (restart the dex container)
plugins/            mounted as the runner's `apisix.plugins` package
  tokenhandler.py   the BFF: endpoints, cookies, CSRF checks, API proxying
  oidc.py           OIDC client: discovery, token endpoint, ID token validation
  sessions.py       server-side session store (in memory)
  trace.py          dev-only traffic trace for the test report
spa/                the Vue SPA (no build step, vendored Vue runtime)
docs/               OAuth/OIDC best practices and where they are implemented
traffic-report/     generated by the tests: sequence diagrams of their traffic
tests/unit/         plugin tests, no gateway needed
tests/integration/  login flow and routing through the running APISIX and Dex
tests/e2e/          the SPA in headless Chromium (Playwright)
tests/traffic/      pytest plugin recording the traffic, report renderer
```

## Workflow

| command                 | does                                                    |
|-------------------------|---------------------------------------------------------|
| `make test`             | all tests                                               |
| `make test-unit`        | unit tests only                                         |
| `make test-integration` | tests against the live gateway                          |
| `make test-e2e`         | SPA browser tests against the live gateway              |
| `make reload`           | apply plugin code and `config.yaml` changes             |
| `make logs`             | follow the APISIX error log (includes runner output)    |
| `make lint`             | ruff                                                    |

Plugin code is loaded once at runner start: after editing `plugins/`, run
`make reload` before running the integration tests.

## Traffic report

Every test run that talks to the gateway writes `traffic-report/index.html`:
one page per test with a sequence diagram of its HTTP traffic (browser,
gateway/BFF, Dex, API). Each message links to its full headers and body, decoded
JWTs and Basic credentials, the PKCE check, and the RFC / OWASP sections it is
an example of. Values the test uses and protocol values (`state`, `code`,
`code_verifier`, tokens, session ids) are highlighted with one color each across
the page; click one to follow it through the flow.

The tests record their own side (`requests` and the Playwright browser). The
BFF records its back channel to Dex, the request it forwards to the API, and
notes on its decisions into `traffic-report/bff-trace.jsonl`, but only for
requests with an `X-Trace-Id` header (only the tests send one), and only because
the dev route config sets `trace_file`. The report contains the dev stack's real
tokens and client secret; never set `trace_file` in production. The recorder
lives in `tests/traffic/` (`-p no:tests.traffic.recorder` turns it off), and a
test can add its own explanation to the diagram with
`tests.traffic.recorder.note(...)`.

## Notes

- The runner has had no release since 0.2.0 (2022). It is cloned at a
  pinned commit, its dependencies are installed with relaxed pins (PyYAML 5.4.1
  does not build on Python 3.11), and one bug is patched (request id 0
  was treated as an error). See `.devcontainer/Dockerfile`.
- `TokenHandler.config()` gets the route's `value` string as-is and parses it
  as JSON.
- The runner can't send two headers of the same name in one response, so the
  BFF uses a single cookie: a login in flight and the logged-in session are
  the same cookie with a new id.
- Sessions live in the runner's memory: `make reload` logs everyone out.
- The SPA uses Vue's runtime-only build with render functions instead of
  templates. The template compiler would need `unsafe-eval` in the CSP. A
  Vite build would allow templates/SFCs under the same CSP; the BFF doesn't
  care either way.
